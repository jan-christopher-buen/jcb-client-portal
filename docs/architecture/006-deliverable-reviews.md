# Versioned deliverable reviews

Later extension: [ADR-007](007-project-handover.md) adds guarded completion/reopening, auditable required flags and explicit change-request/draft resolution. Its rules supersede earlier deferred-completion descriptions below.

Deliverables belong to an organization/project through composite foreign keys. Required flag and stable display order are audited metadata. Text/title/links belong to versions; drafts are owner-only, including a wholly unpublished deliverable. Clients receive only non-draft versions, without owner notes. Reads validate current active membership in a repeatable-read snapshot. Every nested resource identifier is scoped server-side.

A deliverable has at most one draft and one published version, enforced by partial unique indexes. Numbering is unique and bounded to 100. Creating a draft preserves the current pointer; publishing atomically supersedes the previous published snapshot and advances the pointer. Accepted snapshots remain immutable but can be replaced with a reason and a new review. Withdrawn versions remain in history. Withdrawal is limited to an undecided current version. There are no deletion endpoints.

Decisions are immutable unique-per-version receipts with actor, outcome, feedback and UTC timestamp. Identical outcome/feedback retries on the current version return the original receipt. Conflicts, superseded and withdrawn targets return 409. A changed version never inherits acceptance. The UI derives current acceptance from the current version's own receipt, independently of the selected historical version.

All mutations reuse the established serializable organization → enabled actor/current membership → project locking order and bounded conflict retries. Project lock revision coordinates hold/cancellation with delivery workflows. Deliverable revision coordinates metadata, new drafts, publication, withdrawal and decisions; draft revision prevents stale content saves. Publication must present both expected draft and deliverable revisions, so a newly recorded decision forces the owner to reload before replacing it. No external services run inside transactions. State, pointers, receipt, detailed safe event and generic activity event commit or roll back together.

Database constraints bound metadata, content shape, version numbering and feedback. Triggers prevent rewriting published content or decision/event history and validate current authorized decisions. Full URL validation runs server-side through the shared schema on create/edit/publish. The HTTP layer retains session, CSRF and exact Origin controls. SQL operators remain a trusted maintenance boundary; direct database access is not an application authorization interface.

External destinations use WHATWG URL parsing with explicit HTTPS authority, no userinfo, no control/whitespace/backslash or malformed percent escapes, valid multi-label DNS hostname and local-name restrictions. Every IP literal is rejected after URL normalization, including alternative IPv4 encodings and IPv6. No DNS lookup, remote fetch, preview or redirect check occurs. Accepted DNS names can still resolve privately or redirect; validation is not a content-safety or privacy guarantee. React escapes text; links are revalidated before rendering with `target="_blank"`, `rel="noopener noreferrer external"` and `referrerPolicy="no-referrer"`.

Integration tests use independent API servers and Prisma pools, prove overlapping lock waits, test decision/replacement/withdrawal/status/revocation coordination and inject scoped event failures to verify rollback. Only generated fictional fixtures are removed. Published business history has no application deletion workflow.

## Draft recovery

Content editing and new-deliverable creation reuse the offer editor's opt-in resource retention. Forms stay mounted through reloads, refresh failures, list-count changes and unwritable states. Local title, description, stable link rows (including additions/removals), and new-draft required/order fields remain in memory. Reload never advances an existing editor's save revision or replaces local fields. A failed/stale update requires a successful refresh, comparison of the latest title/description/links/revision and explicit reconciliation before retrying. Confirmed discard loads the observed latest version; discarding a failed new draft clears content/links and restores required=true with the latest unused order suggestion.

Creation recovery shows occupied display orders without silently changing the owner's selection. The owner intentionally keeps the draft, chooses a free slot and retries. An occupied slot, unverified/inaccessible resource, published/missing version, held/cancelled/completed project or full deliverable list blocks writes while retaining input. Server authorization, unique-order and conditional-revision checks remain authoritative if another write races after review. Existing duplicate-submit and navigation/unload guards remain in place. This is mounted-memory recovery, not durable autosave; session expiry, refresh or forced exit may lose unsaved input. Metadata-settings editing remains separate from content/new-draft forms.

The opt-in Chromium UI suite covers recovery, explicit reconciliation/discard, links/metadata, access/state changes, duplicate submissions and navigation. It uses fictional HTTP fixtures with the same external Playwright/Chromium prerequisites as offer tests; real-API two-tab and occupied-order journeys are separate local checks.
