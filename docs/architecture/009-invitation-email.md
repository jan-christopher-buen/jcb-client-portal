# Staging invitation email

Production defaults to `disabled`; development/test default to `local`. Explicit `local` remains forbidden in production and SMTP hosts remain loopback-only. `resend` requires a verified sender email, private sending-only key and exact normalized recipient allowlist. Recipient filtering and disabled-mode checks run before invitation creation/revocation. No network or provider SDK runs in transactions. Native fetch uses a fixed HTTPS endpoint, rejects redirects, bounds each attempt to three seconds, and allows at most three attempts within twelve seconds. Retry-After above the inline budget stops sending rather than retrying early. Only transient/network failures retry, using identical JSON and provider idempotency key.

The owner supplies a UUID request key. A unique owner/key index and transaction-scoped owner advisory lock serialize duplicates, even across organizations. The stored organization/email are the immutable request fingerprint; conflicting reuse returns 409. The duplicate path neither generates a token nor invokes delivery. Invitation creation uses READ COMMITTED deliberately: after waiting for advisory locks, subsequent reads must see the preceding commit. Organization row locks preserve reissue/acceptance coordination; a recipient advisory lock enforces a sixty-second cross-organization cooldown for Resend. Existing serializable workflows keep their default isolation and bounded conflict retries.

A committed invitation starts `sending` with a thirty-second deadline. Only its creator holds the raw token, in memory, and attempts email. After the deadline, reads report `unconfirmed`; duplicate lookup also lazily persists this state. No worker or restart resend exists because raw tokens/bodies are never persisted. Deadlines do not revoke tokens. Missing acknowledgement is not proof of failed delivery.

Definitive provider rejection atomically marks failure/revokes and appends safe failure activity. Network ambiguity remains valid and unconfirmed. Provider acceptance recording is a separate transaction: failure there returns unconfirmed and never revokes a possibly accepted invitation. Late updates require a still-sending, unrevoked, unconsumed invitation before its deadline; reissue or acceptance cannot be undone by a late send response. Reissue can race with provider submission, so an already-invalid email may still arrive; no atomic commit across PostgreSQL and the provider is claimed.

`deliveredAt` is retained for schema compatibility and means mail-service acceptance, not confirmed inbox delivery. The API/UI use that wording. No webhooks or inbox receipt guarantee is implemented. Resend deduplicates for 24 hours; application request-key records remain authoritative beyond that window. The UI keeps request identity and recipient after failures/reloads and checks that request without resending. Starting a new request requires explicit confirmation. The HTTP boundary also refuses replacing any earlier unaccepted/unrevoked invitation unless reissueConfirmed is explicitly true, so a full refresh cannot silently replace a link. Closing the page loses transient UI state; inspect owner history before deliberate reissue.

Links keep the exact HTTPS APP_ORIGIN and fragment token, removed into React memory on load. Tokens are posted only in inspection/acceptance bodies and never returned by owner endpoints, persisted in browser storage, or logged. The provider necessarily processes the email body; restrict access to its dashboard. Disable click/open tracking before enabling staging. Existing email-bound new/existing-account acceptance and active-membership authorization are unchanged, including joining another organization.

Only mocked provider HTTP and fictional local fixtures belong in automated tests. No real email, DNS or provider provisioning is part of implementation validation.
